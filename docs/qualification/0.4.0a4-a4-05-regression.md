# PySRMKit - A4-05 Cross-Consumer Regression Qualification

**Cycle:** 4 - Multi-Consumer Integration Qualification  
**Milestone:** `0.4.0a4`  
**Work package:** A4-05 - Cross-Consumer Regression  
**Date:** 2026-10-29  
**Status:** Candidate - CI qualification pending

## 1. Purpose

The existing A4-01 through A4-04 suite qualified the public Python
Supplier search Port, its canonical HTTP adapter on InMemory, SQLite
and PostgreSQL, and the legacy Next.js HTTP consumer. A4-05 adds
deliberate negative and boundary assertions across consumers to stop
a subtle error, pagination edge case or cross-runtime data leak from
passing an isolated happy-path test.

## 2. Scenarios

The executable matrix lives at
`tests/consumers/test_cross_consumer_regression.py`.

| Dimension | Python API | Canonical HTTP | Legacy HTTP | Backend |
| --- | --- | --- | --- | --- |
| Distinct runtimes | Independent Supplier stores | Each host reads only its own store | Same isolated store | InMemory and SQLite |
| Page boundaries | `search(offset, limit)` authoritative | Exact UUID ordering, count and boundaries | Existing list behavior untouched | InMemory and SQLite |
| Validation failures | DTO rejects invalid values | HTTP 422, no side effect | Still accepts the existing list request | InMemory and SQLite |
| Query semantics | Name-only search | Name-only matching and legal-name sort | Broader type/external search; UUID list order | InMemory and SQLite |
| Durable SQL reload | Previously qualified | PostgreSQL real DB, new runtime | Distinct legacy behavior | A4-03 CI #262 |
| Browser compatibility | Not applicable | Opt-in only | Dashboard vendor code and country search | A4-04 CI #265 |

Five pagination cases include offset zero, partial pages and offsets past
the end of the result set. Six invalid input cases exercise syntax/DTO
HTTP error mapping while checking Supplier data is unchanged. Two
independently composed databases exercise isolated reads and prevent
records from leaking between simultaneous HTTP hosts.

## 3. Product and architectural boundaries

- The exact sorting and filtering contract is derived from public
  `SuppliersAPI.search()` and A3's normalized ASCII fixtures.
- No new Unicode collation guarantees: provider-specific casing behavior
  remains documented in ADR 24.
- The legacy dashboard still uses `GET /suppliers`; this package does
  not migrate it to `GET /suppliers/search`.
- The in-process FastAPI TestClient exercises the actual public Facade,
  while the separate A4-04 Playwright E2E verifies the browser stack.
- No multi-tenant security model is claimed: test isolation concerns
  **distinct composition roots/stores**, not authorization or tenancy
  controls.
- PostgreSQL was previously qualified for HTTP search in A4-03.
  A4-05 is a focused InMemory/SQLite consumer regression extension,
  not a replacement for that PostgreSQL evidence.

## 4. Design-learning conventions

**Contract Testing** distinguishes the portable search semantics from
legacy-specific behavior. **Ports & Adapters** keeps the HTTP adapter
thin. **DIP / ISP** retain a narrow public Facade contract. **CQS**
ensures reads and rejected requests do not mutate Supplier records.
**Regression Testing** guards boundary cases in place of large
unrepresentative benchmark fixtures. **KISS/YAGNI** rejects premature
tenant-framework or new persistence infrastructure assumptions.
