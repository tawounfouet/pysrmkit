# PySRMKit — 0.2.0a2 Supplier + Relationship SQL Persistence Qualification

**Milestone:** `0.2.0a2 — Supplier + Relationship SQL Persistence`

## Architecture sentence

> **The existing Supplier and SupplierRelationship Repository Ports can now be satisfied by one SQLAlchemy adapter family across both SQLite and PostgreSQL without changing the Domain or Application layers.**

## Goal

This milestone is the first real test of persistence substitution.

~~~text
SupplierRepository Port
        ^
        |
SqlAlchemySupplierRepository
        |
        +--> SQLite
        +--> PostgreSQL

SupplierRelationshipRepository Port
        ^
        |
SqlAlchemySupplierRelationshipRepository
        |
        +--> SQLite
        +--> PostgreSQL
~~~

No database-specific repository fork was required.

## Persistence records

Implemented tables:

~~~text
suppliers
supplier_external_identifiers
supplier_relationships
~~~

`SupplierRecord` persists the canonical Supplier identity.

`SupplierExternalIdentifierRecord` persists the Aggregate-owned external identifier collection.

`SupplierRelationshipRecord` persists organization-scoped relationship identity and lifecycle state.

## Data Mapper boundary

Domain Aggregates remain ordinary Python objects.

Explicit mappers perform:

~~~text
Domain Aggregate
    -> SQLAlchemy Record

SQLAlchemy Record
    -> Domain.reconstitute(...)
~~~

SQLAlchemy instrumentation never enters Domain classes.

## Repository semantics

Both SQLAlchemy repositories receive an externally created `Session`.

Repository `save()`:

~~~text
stages insert/update state
does not commit
~~~

A dedicated integration test records Session commit events and proves repository save/flush performs zero commits.

This preserves the future use-case transaction boundary.

## Shared Repository Contracts

The existing contract suites are reused without duplicating expected behavior:

~~~text
SupplierRepositoryContract
    +--> InMemorySupplierRepository
    +--> SqlAlchemySupplierRepository / SQLite
    +--> SqlAlchemySupplierRepository / PostgreSQL

SupplierRelationshipRepositoryContract
    +--> InMemorySupplierRelationshipRepository
    +--> SqlAlchemySupplierRelationshipRepository / SQLite
    +--> SqlAlchemySupplierRelationshipRepository / PostgreSQL
~~~

This makes Repository substitution and Liskov Substitution executable rather than merely architectural intent.

## Relationship contract refinement

A real relational FK exposed a legitimate test-harness issue.

The historical Relationship contract creates Relationship Aggregates from arbitrary `SupplierId` values because the InMemory repository does not require another Aggregate to exist.

A SQL database correctly rejects such a row because:

~~~text
supplier_relationships.supplier_id
        ->
suppliers.supplier_id
~~~

The contract therefore gained:

~~~text
prepare_relationship(relationship)
~~~

as a default no-op hook.

The SQL contract implementation uses the hook to prepare the external Supplier precondition.

`SqlAlchemySupplierRelationshipRepository.save()` itself does **not** invent or create Supplier rows.

This preserves repository responsibility boundaries.

## Relational constraints

SQLite integration tests prove:

### Supplier foreign key

A Relationship cannot be flushed when its referenced Supplier does not exist.

### Supplier + organization uniqueness

Two Relationship rows cannot represent the same:

~~~text
SupplierId + InternalOrganizationId
~~~

### External identifier uniqueness

Two Suppliers cannot persist the same normalized external identifier identity:

~~~text
kind
value
source_system
jurisdiction
~~~

These database constraints complement Application pre-checks and protect against concurrent writers.

## Metadata gate evolution

`0.2.0a1` intentionally asserted:

~~~text
PersistenceBase.metadata.tables == empty
~~~

because no business table was justified yet.

That test correctly became invalid in `0.2.0a2`.

The new architecture gate asserts the exact implemented set:

~~~text
suppliers
supplier_external_identifiers
supplier_relationships
~~~

This continues to reject speculative tables while allowing evidence-based ones.
