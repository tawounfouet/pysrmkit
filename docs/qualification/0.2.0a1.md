# PySRMKit — 0.2.0a1 Persistence Foundation Qualification

**Milestone:** `0.2.0a1 — Persistence Foundation`  
**Qualification date:** 2026-10-27  
**Status:** QUALIFIED / GREEN ON PR

## Business / architecture sentence

> **PySRMKit can now construct and test relational persistence infrastructure without making Domain, Application, or Repository Ports depend on SQLAlchemy.**

## Goal

This milestone begins the `0.2.x Persistent Core` cycle by proving the persistence boundary itself before mapping any business Aggregate.

The intended dependency shape is now executable:

~~~text
Domain
  X
  | no SQLAlchemy

Application
  X
  | no SQLAlchemy

Ports
  X
  | no SQLAlchemy

Adapters
  |
  v
pysrmkit.adapters.sqlalchemy
  |
  +--> Engine
  +--> Session factory
  +--> Metadata
  +--> SQLite configuration
~~~

## Dependency packaging

The base package still has zero mandatory third-party runtime dependencies.

SQLAlchemy is exposed through:

~~~text
pysrmkit[persistence]
~~~

with the first Cycle 2 range:

~~~text
sqlalchemy>=2.1,<2.2
~~~

The development extra also installs SQLAlchemy so persistence tests run in the standard CI gate.

## Why SQLAlchemy 2.1

PySRMKit already requires Python 3.11+, which aligns with the SQLAlchemy 2.1 support baseline.

The architecture depends on the `2.1.x` family rather than a single patch release so bug-fix upgrades remain available inside the current series.

## Persistence package

Added:

~~~text
src/pysrmkit/adapters/sqlalchemy/
├── __init__.py
├── metadata.py
├── engine.py
└── session.py
~~~

No capability-specific persistence package exists yet.

That omission is intentional.

## PersistenceBase

`PersistenceBase` is a SQLAlchemy `DeclarativeBase` owned by the persistence adapter.

At this milestone:

~~~text
PersistenceBase.metadata.tables == empty
~~~

This proves the foundation does not pre-create speculative Supplier, Relationship, Onboarding, Assessment, or Qualification tables.

## Engine ownership

`create_persistence_engine(...)` constructs an Engine only when explicitly called.

There is:

~~~text
no global Engine
no Engine at import time
no environment-variable read inside Domain
no hidden database connection during package import
~~~

The composition/runtime boundary remains responsible for supplying a database URL.

## SQLite foreign-key enforcement

SQLite does not provide the relational safety required by this architecture unless foreign-key enforcement is explicitly enabled.

The Engine factory therefore registers connection-level configuration:

~~~text
PRAGMA foreign_keys = ON
~~~

The test suite proves both:

1. the PRAGMA reports enabled;
2. inserting a child row that references a missing parent raises a database integrity failure.

This makes the SQLite configuration behavioral rather than decorative.

## Session factory

`create_session_factory(engine)` receives an externally owned Engine and creates SQLAlchemy Sessions bound to it.

This establishes the direction:

~~~text
Composition Root
    -> Engine
    -> Session factory
    -> Session
    -> future SQL repositories
~~~

Repositories do not create Engines.

## Sync-first

The foundation is synchronous.

No `AsyncEngine` or `AsyncSession` was introduced.

This preserves one execution model until asynchronous persistence becomes a real requirement.

## Architecture fitness rules

The architecture test suite now additionally forbids these imports from Domain, Application, and Ports:

~~~text
sqlalchemy
alembic
psycopg
~~~

This turns the persistence-ignorance decision from documentation into executable architecture.
