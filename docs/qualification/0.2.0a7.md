## Transaction strategy

No global UnitOfWork was introduced.

Single-repository use cases keep the existing architecture:

~~~text
Handler
    ↓
Repository.save(...)
    ↓
composition root owns Session.commit()
~~~

The one multi-Aggregate use case continues to use the already justified capability-specific boundary:

~~~text
StartSupplierOnboardingHandler
    ↓
SqlAlchemySupplierOnboardingUnitOfWork
    ├── SupplierRelationshipRepository
    └── SupplierOnboardingRepository
~~~

This preserves Problem Before Pattern:

> **one demonstrated atomic multi-Aggregate pressure produced one UnitOfWork; the final scenario did not manufacture a global one.**

## Post-commit event publication

Most existing single-repository handlers dispatch Domain Events before an external SQL commit because they remain persistence-agnostic.

The persistent composition root therefore introduces:

~~~text
DeferredDomainEventDispatcher
~~~

Its semantics are:

~~~text
Handler dispatch(...)
    ↓
buffer only

Session.commit()
    ↓
success
    ↓
publish buffered events

or

Session.commit()
    ↓
failure
    ↓
rollback
discard buffered events
~~~

The existing onboarding UnitOfWork already commits internally before the Handler dispatches its event. The deferred dispatcher is flushed immediately after that Handler returns.

This mechanism is deliberately small.

It is **not** a Transactional Outbox.

The remaining crash window:

~~~text
database COMMIT
    ↓
process crashes
    ↓
in-process event not published
~~~

is explicitly deferred.

## The restart boundary

The central qualification step is not merely opening another repository object in the same Session.

The scenario performs:

~~~text
business execution
    ↓
commit final Qualification
    ↓
close Session
    ↓
discard Repository instances
    ↓
dispose original Engine
    ↓
create NEW Engine
    ↓
create NEW Session factory
    ↓
create NEW Session
    ↓
create NEW Repository instances
    ↓
reload durable Aggregate state
~~~

Final assertions are made only against the reloaded Domain objects.

## First implementation failure: committed owned collections

The first PostgreSQL run failed during the onboarding update after a real commit.

The sequence was:

~~~text
create Onboarding
    ↓
COMMIT
    ↓
reload Onboarding
    ↓
satisfy LEGAL_NAME
    ↓
save
    ↓
COMMIT
    ↓
UNIQUE violation
~~~

The collision was:

~~~text
uq_supplier_onboarding_requirement_code

(onboarding_id, LEGAL_NAME)
already exists
~~~

## Why earlier Repository Contracts did not expose it

The earlier SQL Repository Contracts proved logical save/reload behavior inside one test transaction.

Their update shape was effectively:

~~~text
save
    ↓
autoflush / reload
    ↓
mutate
    ↓
save
    ↓
rollback at test teardown
~~~

The persistent scenario introduced the missing pressure:

~~~text
save
    ↓
COMMIT
    ↓
reload persisted technical rows
    ↓
mutate
    ↓
save
    ↓
COMMIT
~~~

This is materially different for ORM-owned collections.

## Root cause

The original Data Mapper update strategy replaced owned child collections wholesale:

~~~text
Domain requirements
    ↓
create brand-new OnboardingRequirementRecord objects
    ↓
assign record.requirements = new_rows
~~~

After the first commit, old child rows already had database identity and unique business keys.

SQLAlchemy could therefore attempt to insert the replacement row before deleting the original row:

~~~text
existing LEGAL_NAME row
    +
new LEGAL_NAME row
    ↓
UNIQUE violation
~~~

The same structural risk existed for Assessment question/answer children.

## Corrected Data Mapper rule

Owned collections are now reconciled using the stable identity that already exists in the Domain.

Onboarding:

~~~text
OnboardingRequirement.code
    ↓
match existing persistence row
    ↓
update row in place
~~~

Assessment:

~~~text
AssessmentQuestion.code
    ↓
match existing persistence question row

AssessmentAnswer.question_code
    ↓
match existing persistence answer row
~~~

Technical database identifiers remain hidden:

~~~text
requirement_id
question_id
answer_id
~~~

The Domain does not gain persistence IDs merely to make the ORM convenient.

This preserves:

~~~text
Domain identity semantics
        +
Data Mapper separation
        +
Information Hiding
~~~

## Design principle learned

The milestone makes a useful distinction explicit:

> **Replacing a Domain-owned collection is not necessarily equivalent to replacing its persisted rows.**

A Data Mapper must bridge:

~~~text
Domain identity
    ↔
persistence identity
~~~

without leaking the persistence identity inward.

For owned objects with stable Domain keys, reconciliation is preferable to destructive row recreation when durable updates occur.
