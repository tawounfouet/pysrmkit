## Business sentence

> **A SupplierRelationship can reach a domain-valid onboarding state whose readiness is explicit and usable by later qualification rules.**

## Goal

The milestone introduces the minimum onboarding model needed by the local qualification path without turning PySRMKit into a workflow engine.

~~~text
business onboarding state
        ≠
workflow orchestration
~~~

## Aggregate boundary decision

Implementation pressure justified SupplierOnboarding as a relationship-scoped Aggregate Root.

It owns:

- a stable onboarding identity;
- relationship ownership;
- onboarding requirements;
- requirement satisfaction state;
- completion invariant;
- completion event.

The Aggregate boundary became useful because onboarding now has independent application use cases and repository persistence.

## Relationship ownership

Every onboarding references exactly one SupplierRelationshipId.

The MVP application rule allows only one current onboarding per Relationship.

Cross-instance existence is checked through SupplierOnboardingRepository.find_for_relationship(...) before a new onboarding is created.

## Start use case refinement

No duplicate CreateSupplierOnboarding command was added.

Instead, the existing StartSupplierOnboarding use case now performs the cohesive operation:

1. load the Relationship;
2. verify there is no current onboarding;
3. validate the Relationship lifecycle transition;
4. move the Relationship to ONBOARDING;
5. create SupplierOnboarding;
6. persist both Aggregates;
7. dispatch the existing SupplierOnboardingStarted event from the Relationship.

This follows the roadmap instruction to avoid a duplicate create command when lifecycle start already owns the business intent.

## Domain objects

~~~text
OnboardingId
OnboardingRequirementCode
OnboardingRequirement
OnboardingProgress
SupplierOnboarding
~~~

### OnboardingRequirement

Each requirement has code, mandatory semantics, and a satisfied state.

The Value Object is immutable. Satisfaction replaces requirement state inside the Aggregate rather than mutating a shared external object.

## OnboardingProgress

OnboardingProgress is a computed Domain Result containing totals, satisfied counts, missing mandatory requirements, readiness, and completion.

It is deliberately not an Entity and is not persisted as the source of truth. Canonical state remains the onboarding requirements.

## Completion invariant — ONB-001

> **Mandatory onboarding requirements must be satisfied before completion.**

Attempting completion with missing mandatory requirements raises MandatoryOnboardingRequirementsNotSatisfied and guarantees:

~~~text
completed state unchanged
+
no completion Domain Event
~~~

Optional unsatisfied requirements do not block completion.

## Domain Events

The existing relationship lifecycle event SupplierOnboardingStarted remains the unique start event.

No second onboarding-start event is emitted by SupplierOnboarding, avoiding two Domain Events for the same business fact.

The new Aggregate emits SupplierOnboardingCompleted when completion succeeds.

## InMemory adapter

InMemorySupplierOnboardingRepository snapshots onboarding_id, relationship_id, started_at, requirements, and completed_at, then reconstitutes a fresh Aggregate on reads.

The shared contract proves save/get round trip, absent behavior, relationship lookup, satisfaction/completion round trips, unsaved-change isolation, and relationship isolation.

## Architecture checkpoint

This milestone is the first use case that persists two Aggregates in one application operation:

~~~text
SupplierRelationship
+
SupplierOnboarding
~~~

This creates real transaction-boundary pressure.

A UnitOfWork was **not** introduced yet. A NoOp UnitOfWork would make a transaction boundary visible without providing rollback or true atomicity across the current InMemory repositories.

The pressure is recorded for future persistence work, where a real transactional adapter can justify the pattern.

## Why no OnboardingStage

The pre-implementation model listed OnboardingStage as a candidate, but the first implementation does not need it.

For the local qualification path, the meaningful facts are requirements, satisfaction, readiness, and completion.

Adding an onboarding-specific state machine now would duplicate lifecycle complexity without a demonstrated use case. This is an explicit YAGNI decision.
