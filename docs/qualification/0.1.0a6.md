# PySRMKit — 0.1.0a6 Qualification Domain Qualification

**Milestone:** `0.1.0a6 — Qualification Domain`  
**Qualification date:** 2026-10-27  
**Status:** QUALIFIED / GREEN ON PR

## Business sentence

> **The Qualification Domain can request, evaluate, explain, approve, reject, emit events, and persist scoped qualifications without any Application Handler.**

## Goal

This milestone implements the central qualification capability independently from final Application orchestration.

The execution boundary is:

~~~text
Facts
  ↓
QualificationContext
  ↓
QualificationPolicy
  ↓
QualificationDecision
  ↓
SupplierQualification.apply_decision(...)
~~~

Application handlers are deliberately absent from this milestone.

## Qualification scope

`QualificationScope` explicitly answers:

> **Qualified for what?**

The first implementation supports the minimum dimensions already justified by the specification:

~~~text
organization_id?
category_code?
country_code?
~~~

At least one dimension is mandatory.

Therefore this is invalid:

~~~text
QualificationScope()
~~~

and scoped qualification never collapses into a global `supplier.is_qualified = True` flag.

Business-unit, capability, service-type, and financial-limit dimensions remain deferred until a concrete use case requires them.

## Qualification statuses

The reference status vocabulary is represented:

~~~text
PENDING
QUALIFIED
NOT_QUALIFIED
REVOKED
EXPIRED
~~~

The first vertical slice fully implements only:

~~~text
PENDING → QUALIFIED
PENDING → NOT_QUALIFIED
~~~

Revocation and expiration are represented as vocabulary/currentness boundaries but do not yet expose mutation behavior.

## QualificationDecision

The Decision Object contains:

~~~text
approved
resulting_status
reasons
failed_requirements
decided_at
~~~

It protects consistency:

- approved decisions must result in `QUALIFIED`;
- approved decisions cannot contain failed requirements;
- rejected decisions must result in `NOT_QUALIFIED`;
- every decision must contain an explanation.

This prevents contradictory state such as:

~~~text
approved = False
status = QUALIFIED
~~~

## QualificationContext

The first policy consumes pre-collected facts rather than infrastructure objects:

~~~text
onboarding_complete
assessment_completed
assessment_score
required_answers_complete
~~~

The Context contains facts only. It does not contain database sessions, HTTP clients, SDK objects, or generic dictionaries.

## QualificationPolicy

`QualificationPolicy` is a concrete deterministic Domain Policy.

The first policy requires:

1. onboarding to be complete;
2. assessment to be complete;
3. assessment score to be available;
4. assessment score to reach the configured minimum;
5. required assessment answers to be complete.

The default minimum assessment score is 80.

The Policy returns a full `QualificationDecision`, never a bare boolean.

### Explainability

Rejected decisions contain stable failed-requirement codes such as:

~~~text
ONBOARDING_COMPLETE
ASSESSMENT_COMPLETE
ASSESSMENT_SCORE_AVAILABLE
ASSESSMENT_MINIMUM_SCORE
REQUIRED_ANSWERS_COMPLETE
~~~

plus human-readable reasons.

Multiple failures are preserved in deterministic evaluation order.

## Strategy Pattern decision

The design pressure justifies a replaceable Domain Policy boundary, but not yet a hierarchy of speculative implementations.

Therefore the first implementation uses:

~~~text
QualificationPolicy
~~~

as the concrete policy itself rather than introducing both an abstract `QualificationPolicy` and a `DefaultQualificationPolicy` before a second strategy exists.

This keeps the Strategy concept explicit while applying YAGNI to the class hierarchy.

## SupplierQualification Aggregate

`SupplierQualification.request(...)` creates a Qualification in:

~~~text
PENDING
~~~

and records:

~~~text
SupplierQualificationRequested
~~~

`apply_decision(...)` is guarded so only a pending Qualification can receive its first decision.

An approved Decision produces:

~~~text
QUALIFIED
+
SupplierQualified
~~~

A rejected Decision produces:

~~~text
NOT_QUALIFIED
+
SupplierQualificationRejected
~~~

A second decision attempt is rejected without changing state or emitting a success event.

## Domain Events

Implemented:

~~~text
SupplierQualificationRequested
SupplierQualified
SupplierQualificationRejected
~~~

Event payloads use domain vocabulary: Qualification ID, Relationship ID, Scope, occurrence time, and rejection reasons where relevant.

Rehydration does not recreate historical events.

## Repository Port

`SupplierQualificationRepository` exposes only:

~~~text
get
save
find_current_for_scope
~~~

The current lookup is explicitly keyed by:

~~~text
SupplierRelationshipId
+
QualificationScope
~~~

which prepares the cross-instance uniqueness rule for `0.1.0a7` without placing it inside one isolated Aggregate.

## Repository contract

The InMemory adapter contract verifies:

- save/get round trip;
- unknown ID returns `None`;
- current lookup by Relationship + Scope;
- different scopes do not collide;
- different Relationships do not collide;
- status/decision survive explicit save/reload;
- unsaved decisions do not leak into storage;
- expired historical Qualifications are not returned as current;
- rehydration creates no historical events.
