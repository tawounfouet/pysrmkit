## Architecture sentence

> **The Persistent Core relational schema can now be created reproducibly from an empty supported database through a versioned Alembic history, without moving persistence concerns into Domain, Application, or Repository Ports.**

## Pressure that justified Alembic

By 0.2.0a5, SQLAlchemy persistence already proved the complete current Aggregate set on SQLite and PostgreSQL.

The missing capability was no longer ORM persistence:

~~~text
PersistenceBase.metadata.create_all(...)
    ✅ creates current schema

but

versioned schema history
    ❌ absent
~~~

The Persistent Core therefore needed a reproducible schema-bootstrap mechanism independent from repository behavior tests.

## Persistence metadata registration

Alembic needs the complete SQLAlchemy metadata graph even though normal package import must remain side-effect free.

The milestone therefore adds an explicit infrastructure helper:

~~~text
load_persistence_metadata()
    ↓
imports persistence model registry
    ↓
returns PersistenceBase.metadata
~~~

This makes migration discovery explicit without teaching Domain or Application about persistence models.

## Deterministic naming convention

The SQLAlchemy persistence metadata now owns deterministic names for:

~~~text
PK
FK
UQ
CHECK
INDEX
~~~

The first attempted foreign-key convention included the referred table:

~~~text
fk_<table>_<column>_<referred_table>
~~~

Real PostgreSQL qualification rejected:

~~~text
fk_supplier_onboarding_requirements_onboarding_id_supplier_onboardings
~~~

because PostgreSQL identifiers are limited to 63 characters.

The convention was therefore refined to:

~~~text
fk_<table>_<column>
~~~

This remains deterministic and meaningful while fitting the reference backend.

## SQLite qualification

The SQLite migration tests prove:

~~~text

    ↓

    ↓

~~~

and:

~~~text

    ↓
downgrade base
    ↓
no business tables
    ↓

    ↓

~~~

The migrated schema is checked against SQLAlchemy metadata for table names, column names, primary keys, foreign keys, unique constraints, check constraints, and explicit indexes.

## PostgreSQL qualification

The PostgreSQL 18.6 job proves:

~~~text
empty PostgreSQL database
    ↓
alembic upgrade head
    ↓
complete Persistent Core schema
    ↓
alembic upgrade head again
    ↓
still current / no duplicate migration
~~~

PostgreSQL also exposed an important reflection distinction:

~~~text
logical UNIQUE CONSTRAINT
    ↓
physical backing index
~~~

PostgreSQL may expose that backing index through Inspector.get_indexes().

The qualification therefore compares unique constraints separately from explicit SQLAlchemy indexes instead of requiring dialect-identical physical reflection.

## Repository behavior remains separate

Focused Repository Contract and SQL behavior tests may continue using PersistenceBase.metadata.create_all(engine) when the subject under test is repository behavior rather than migration history.

Migration correctness is now tested separately through Alembic.

This preserves fast contract tests without confusing:

~~~text
current metadata materialization
        with
versioned schema evolution
~~~

## Implementation feedback

This milestone produced two useful pieces of real infrastructure pressure.

### 1. Identifier length is a backend constraint

A naming convention can be deterministic and still be invalid for a target database.

PostgreSQL forced the convention to become both:

~~~text
stable
+
portable enough for the reference backend
~~~

No Domain or Repository Port change was needed.

### 2. Schema equivalence is not physical-reflection identity

SQLite and PostgreSQL can implement the same logical uniqueness semantics while exposing indexes differently through introspection.

The correct compatibility rule remains:

~~~text
same logical schema meaning
same business constraints
same Repository behavior
~~~

not:

~~~text
identical dialect reflection
~~~
