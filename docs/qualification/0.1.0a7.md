# PySRMKit — 0.1.0a7 Qualification Application Flow Qualification

**Milestone:** `0.1.0a7 — Qualification Application Flow`  
**Qualification date:** 2026-10-27  
**Status:** QUALIFIED / GREEN

## Business sentence

> **Assessment, Relationship, Onboarding, and Qualification now cooperate through explicit Application handlers while business decisions remain inside Domain Policies and Aggregates.**

## Goal

The milestone connects the previously isolated domain capabilities without moving qualification rules into the Application Layer.

~~~text
Repositories collect state
        ↓
Application Handler coordinates
        ↓
QualificationPolicy decides
        ↓
SupplierQualification enforces
        ↓
Repository persists
        ↓
DomainEventDispatcher dispatches
~~~

## Assessment minimum

The first qualification flow required a concrete Assessment capability.

Implemented:

~~~text
AssessmentId
AssessmentType
AssessmentQuestion
AssessmentAnswer
AssessmentScore
AssessmentDecision
SupplierAssessment
~~~

`SupplierAssessment` is Relationship-scoped and represents one identifiable assessment execution.

### Question snapshots

Questions are immutable Value Objects stored inside the Assessment execution.

Each question carries:

~~~text
code
mandatory
maximum_score
~~~

This preserves the historical scoring structure used by that Assessment without introducing a separate questionnaire-definition engine.

### Answers

An answer carries:

~~~text
question_code
score
~~~

The Aggregate enforces:

- answer refers to a known question;
- answer score is non-negative;
- answer score does not exceed that question's maximum.

### Completion

Mandatory questions must have answers before `complete(...)` succeeds.

After completion:

~~~text
SupplierAssessment
    becomes immutable by default
~~~

and records:

~~~text
SupplierAssessmentCompleted
~~~

## Assessment scoring

The first implementation computes a deterministic percentage:

~~~text
sum(answer scores) * 100
------------------------
sum(question maximums)
~~~

using integer percentage semantics.

Optional unanswered questions do not block completion, but they contribute zero earned points to this first scoring model.

This scoring behavior is deliberately minimal and can evolve only when a richer Assessment use case creates real pressure.

## AssessmentDecision boundary

`AssessmentDecision` is intentionally distinct from `QualificationDecision`.

An Assessment may carry:

~~~text
APPROVED
REJECTED
REVIEW_REQUIRED
~~~

but the Qualification Policy does not automatically copy this value into qualification state.

This preserves the invariant:

~~~text
Assessment result
        ≠
Qualification decision
~~~

## Assessment repository

`SupplierAssessmentRepository` exposes:

~~~text
get
save
find_latest_for_relationship
~~~

The latest lookup exists because Qualification evaluation needs the current Assessment facts for one Relationship.

The contract proves:

- save/get round trip;
- absent ID behavior;
- latest Assessment selection;
- answer/completion persistence;
- unsaved-change isolation;
- Relationship isolation.

## Assessment application flows

Implemented:

~~~text
CreateSupplierAssessment
RecordAssessmentAnswer
CompleteSupplierAssessment
~~~

`CreateSupplierAssessmentHandler` verifies that the target Relationship exists.

`CompleteSupplierAssessmentHandler` uses `Clock`, persists the completed Aggregate, and dispatches `SupplierAssessmentCompleted`.

## Qualification request flow

Implemented:

~~~text
RequestSupplierQualification
RequestSupplierQualificationHandler
~~~

The Handler:

1. loads the Relationship;
2. fails explicitly if it does not exist;
3. checks `find_current_for_scope(RelationshipId, QualificationScope)`;
4. rejects duplicate current scope using `CurrentQualificationAlreadyExists`;
5. requests the Domain Aggregate;
6. saves it;
7. dispatches `SupplierQualificationRequested`.

This makes QUAL-006 executable at the correct boundary:

~~~text
Application orchestration
+
Repository lookup
~~~

rather than inside one isolated Aggregate.

## Qualification evaluation flow

Implemented:

~~~text
EvaluateSupplierQualification
EvaluateSupplierQualificationHandler
~~~

The Handler performs orchestration only:

1. load SupplierQualification;
2. load Relationship-scoped Onboarding facts;
3. load latest Relationship-scoped Assessment facts;
4. build `QualificationContext`;
5. invoke the injected `QualificationPolicy`;
6. pass the returned Decision to `SupplierQualification.apply_decision(...)`;
7. persist the Qualification;
8. dispatch the recorded Domain Event;
9. return the final status and Decision.

## Important rule placement

The Handler contains no rule equivalent to:

~~~python
if assessment.score >= 80:
    qualification.status = QUALIFIED
~~~

Instead:

~~~text
Handler
  collects facts
        ↓
QualificationPolicy
  decides
        ↓
SupplierQualification
  enforces transition
~~~

This is the main architectural exit condition of `a7`.

## Cross-capability boundaries

The tests explicitly prove:

~~~text
Assessment completion
    does NOT directly mutate Qualification

Qualification evaluation
    does NOT directly mutate Relationship

Application
    coordinates capabilities explicitly
~~~

A qualified `SupplierQualification` can therefore coexist with a Relationship that remains in `ONBOARDING` until a separate lifecycle use case decides otherwise.

## In-process event dispatch

Implemented:

~~~text
InProcessDomainEventDispatcher
~~~

It dispatches synchronously by exact Domain Event type and preserves handler registration order.

No broker, queue, asynchronous runtime, retry system, or Integration Event mapping was introduced.

## UnitOfWork checkpoint

The roadmap requires an explicit decision at this milestone.

`UnitOfWork` remains deferred.

Reason:

- Assessment create/record/complete writes one Assessment Aggregate per command;
- Qualification request writes one Qualification Aggregate;
- Qualification evaluate reads multiple Aggregates but writes one Qualification Aggregate;
- persistence is still InMemory and has no real transactional resource to commit.

Adding a NoOp UnitOfWork would add ceremony without providing atomicity or rollback.

This preserves the project's `Problem before Pattern` convention.
