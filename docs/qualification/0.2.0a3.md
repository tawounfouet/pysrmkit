## Architecture sentence

> **Relationship-scoped Onboarding and Assessment Aggregates now persist their owned collections and business timestamps through the same SQLAlchemy adapter family on SQLite and PostgreSQL without changing Domain or Repository Port APIs.**

## Implemented persistence shape

~~~text
supplier_onboardings
└── supplier_onboarding_requirements

supplier_assessments
├── supplier_assessment_questions
└── supplier_assessment_answers
~~~

Both Aggregate roots reference real `supplier_relationships` rows.

## Data Mapper boundary

Domain Aggregates remain persistence-ignorant. Explicit mappers flatten and reconstruct:

~~~text
SupplierOnboarding
  requirements[]
  started_at
  completed_at

SupplierAssessment
  questions[]
  answers[]
  assessment_type
  created_at
  completed_at
  score
  decision
~~~

No SQLAlchemy instrumentation enters Domain classes.

## Ordered owned collections

Requirement, question, and answer rows persist an explicit technical `position`.

This preserves Domain snapshot ordering without treating order as database insertion accident.

## UTC timestamp boundary

SQLite does not preserve timezone information like PostgreSQL.

`UTCDateTime` therefore:

- rejects naive datetimes on write;
- normalizes aware values to UTC;
- restores timezone-aware UTC values on read.

The existing Repository Contract completion timestamps now pass unchanged on both SQLite and PostgreSQL.

## Assessment Answer → Question relationship

The first PostgreSQL run exposed a real persistence-model issue.

A composite FK using `assessment_id + question_code` expressed SQL integrity, but SQLAlchemy did not have an explicit object dependency to guarantee Question INSERT before Answer INSERT.

The persistence model was refined to:

~~~text
AssessmentAnswerRecord
    question_id
        ↓
AssessmentQuestionRecord.question_id
~~~

with an explicit ORM relationship.

`question_id` is a persistence-only surrogate key. The Domain continues to identify answers by `question_code`.

This is a concrete example of:

~~~text
Persistence model
    may need technical identity
        ≠
Domain identity vocabulary
~~~

## Shared Repository Contracts

Existing contracts now execute against:

~~~text
SupplierOnboardingRepositoryContract
├── InMemory
├── SQLAlchemy / SQLite
└── SQLAlchemy / PostgreSQL

SupplierAssessmentRepositoryContract
├── InMemory
├── SQLAlchemy / SQLite
└── SQLAlchemy / PostgreSQL
~~~

Relationship-scoped contract harnesses gained default no-op preparation hooks. SQL implementations use them only to prepare required parent Aggregates.

Repositories themselves never invent missing Relationships.

## Relational constraints

SQLite integration tests prove:

- Onboarding requires an existing Relationship;
- Assessment requires an existing Relationship;
- one Onboarding row is allowed per Relationship;
- Assessment Answer requires a real Question row.

These constraints complement Domain/Application invariants.
