# PySRMKit — 0.2.0a5 Transaction Boundary / UnitOfWork Qualification

**Milestone:** `0.2.0a5 — Transaction Boundary / UnitOfWork`  
**Qualification date:** 2026-10-27  
**Status:** QUALIFIED / GREEN ON PR

## Architecture sentence

> **The first SQL-backed multi-Aggregate use case now executes through an explicit UnitOfWork that owns a shared transaction boundary and dispatches Domain Events only after commit succeeds.**

## Pressure that justified the pattern

`StartSupplierOnboarding` writes two Aggregate roots:

~~~text
SupplierRelationship
        +
SupplierOnboarding
~~~

With real SQL persistence, partial success would be invalid:

~~~text
Relationship = ONBOARDING
but
SupplierOnboarding row missing
~~~

That is the concrete pressure that finally justified UnitOfWork.

## Why the UnitOfWork is capability-specific

The project does not introduce one global object exposing every repository.

Instead:

~~~text
SupplierOnboardingUnitOfWork
├── relationship_repository
└── onboarding_repository
~~~

This is the smallest boundary that solves the demonstrated transaction problem.

## Application flow

`StartSupplierOnboardingHandler` now executes:

~~~text
enter UnitOfWork
    ↓
load Relationship
    ↓
check existing Onboarding
    ↓
Relationship.start_onboarding(...)
    ↓
create SupplierOnboarding
    ↓
save Relationship
save Onboarding
    ↓
pull Domain Events
    ↓
commit
    ↓
exit transaction
    ↓
dispatch Domain Events
~~~

The event dispatcher is therefore outside the transaction block.

## InMemory UnitOfWork

The InMemory adapter is not a NoOp transaction.

It captures Domain-state snapshots of both repositories before the use case.

On rollback it restores:

~~~text
SupplierRelationship state
SupplierOnboarding state
~~~

This means the Application contract remains meaningful even without SQL.

## SQLAlchemy UnitOfWork

The SQLAlchemy adapter creates one Session and constructs both repositories from that same Session.

~~~text
SqlAlchemySupplierOnboardingUnitOfWork
        ↓
one Session
        ├── SqlAlchemySupplierRelationshipRepository
        └── SqlAlchemySupplierOnboardingRepository
~~~

Repositories still never call `commit()`.

The UnitOfWork owns:

~~~text
commit
rollback
Session close
~~~

## Commit failure semantics

A test-only Session forces failure after flush during `commit()`.

The qualified result is:

~~~text
relationship stage -> INVITED
onboarding row     -> absent
dispatched events  -> none
~~~

This proves atomic rollback after both repository writes have already been staged.

## Event ordering

The Handler records/pulls `SupplierOnboardingStarted` before commit, but dispatches it only after successful commit.

Therefore:

~~~text
commit FAIL
    -> rollback
    -> no event dispatch

commit SUCCESS
    -> durable state
    -> event dispatch
~~~

This is the first executable post-commit Domain Event ordering rule in PySRMKit.

## SQLite qualification

SQLite proves:

- successful atomic Relationship + Onboarding commit;
- rollback after forced commit failure;
- no event after failed commit;
- final persisted Relationship stage;
- final Onboarding existence.

## Implementation feedback

The milestone exposed useful design pressure:

1. Ruff caught only formatting/import issues.
2. Pyright rejected coupling the InMemory UnitOfWork to private `_Stored*` repository types.
3. The InMemory transaction boundary was therefore improved to snapshot/reconstruct **Domain state** instead of repository-internal storage details.
4. No Domain model or Repository Port had to change.
